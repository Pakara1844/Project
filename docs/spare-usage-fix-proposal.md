# ข้อเสนอการแก้ไข — Logic การใช้ Spare ของตัวเลือกสับเปลี่ยน

> สถานะ: **ร่างข้อเสนอ (ยังไม่แก้โค้ด)** · อ้างอิง v9.2 · วันที่ 2026-11-06
> ผู้จัดทำ: เพื่อทบทวนร่วมกับทีมก่อนลงมือแก้

---

## 1. อาการที่พบ

- ใส่ spare เข้าไปจำนวนหนึ่ง → ระบบ **ใช้ spare เกือบ/ทั้งหมด** ทั้งที่จริง ๆ อาจไม่จำเป็นต้องใช้หมด
- เพิ่มจำนวน spare เข้าไปอีก → ระบบก็ **ดึง spare ที่เพิ่มมาใช้อีก**
- ความรู้สึก: ของใหม่พึ่ง spare มากกว่าที่ควร ทั้งที่เปิดให้ "สลับข้ามเฟสในแร็ค" ได้แล้ว น่าจะบาลานซ์ได้โดยไม่ต้องเปลือง spare

---

## 2. สาเหตุราก (root cause)

ลำดับการตัดสินใจเลือกแผนอยู่ที่ 2 ฟังก์ชัน ที่ใช้เกณฑ์เดียวกัน:

- `better()` — [`src/js/calculator.js:775`](../src/js/calculator.js) (เลือกผู้ชนะต่อ budget ภายใน search)
- `chooseBudget()` — [`src/js/calculator.js:1216`](../src/js/calculator.js) (เลือกข้าม level L0/L1)

**ลำดับปัจจุบัน** (หลังผ่าน gate):

| ลำดับ | เกณฑ์ |
|---|---|
| 1 | ผ่านรีเลย์ (I_no < threshold) — *gate* |
| 2 | บาลานซ์เฟส (spread ≤ 0.005 µF) — *gate แบบ boolean* |
| 3 | **I_no ต่ำสุด**  ← ตัวตัดสินหลัก |
| 4 | `cost` (ใกล้→ไกล, spare ท้ายสุด) |
| 5 | สับน้อยครั้งสุด |
| 6 | ใช้ spare น้อยสุด (`sp`) |

**ปัญหา:** ข้อ 3 (I_no ต่ำสุด) มาก่อนข้อ 4–6 เสมอ → **พอผ่านครบทั้งรีเลย์+บาลานซ์แล้ว ระบบยังไล่กด I_no ต่อ**

spare เป็นคาปตัวใหม่ค่า ~27 µF พอดี → การแทนตัวเพี้ยนด้วย spare **มักกด I_no ได้ต่ำกว่า**การสลับในแร็ค (ซึ่งแค่ย้ายความไม่สมดุลไปมา) ดังนั้น:

- แผนที่ใช้ spare มักชนะเพราะ I_no ต่ำกว่า
- ยิ่งใช้ spare หลายตัว I_no ยิ่งต่ำลงอีกนิด → ลากไปใช้ **ทุกตัวเท่าที่ budget อนุญาต**
- เกณฑ์ข้อ 4 (`cost` spare-ท้ายสุด) และข้อ 6 (spare น้อยสุด) อยู่ **ใต้ I_no** → ต้อง I_no เท่ากันเป๊ะ (< 1e-9) ถึงจะมีผล ซึ่งแทบไม่เกิด → เหมือน "ตายตั้งแต่เกิด"

### จุดที่ป้อน candidate ที่ใช้ spare เข้ามา
- **beam track** — spare replacement ลองแทน spare กับ *ทุกตัว* ไม่มี guard: [`calculator.js:488`](../src/js/calculator.js)
- **Track 3 route** — ใช้ spare เพื่อไปถึง arrangement เป้าหมาย: [`calculator.js:719`](../src/js/calculator.js)
- **outlier-fix track** — มี guard อยู่แล้ว (ข้ามตัวดีที่อยู่ใกล้ mode `dev<0.02 && !bad`) → ตัวนี้ **ไม่ใช่** ต้นเหตุหลัก: [`calculator.js:633`](../src/js/calculator.js)
- **budget ตัวที่ 3 = 12 (MAX)** ออกแบบให้ "ใช้ทรัพยากรเต็มที่": [`calculator.js:361`](../src/js/calculator.js)

> หมายเหตุ: การ์ด "⭐ แนะนำ" ใน ui.js เลือก *fewest swaps ที่ผ่าน* อยู่แล้ว ([`ui.js:179`](../src/js/ui.js)) แต่ candidate ของแต่ละ budget ที่ส่งเข้ามานั้นเป็นแผน spare-เยอะมาตั้งแต่ `chooseBudget` → **ต้องแก้ที่ ranking เป็นหลัก** แก้แค่ ui.js ไม่พอ

## 3. หลักการที่เสนอใหม่

> **"ผ่านแล้วพอ — แล้วค่อยประหยัด"**
> เมื่อแผนผ่านทั้งรีเลย์และบาลานซ์เฟสแล้ว ให้ถือว่า "ดีพอสำหรับหน้างาน" และหันไปเลือกแผนที่ **ประหยัด spare / แรงงานน้อยสุด** แทนการไล่กด I_no ให้เข้าใกล้ศูนย์โดยเปลือง spare

ประกอบด้วย 2 ส่วน:

### ส่วน A — สลับลำดับความสำคัญหลังผ่านครบ 2 gate
เพิ่ม "สาขาผ่านครบ" แยกออกมา: ถ้าทั้งสองแผน **ผ่านรีเลย์ + บาลานซ์** ให้เรียงแบบนี้แทน

| ลำดับใหม่ (เมื่อผ่านครบทั้งคู่) | เกณฑ์ |
|---|---|
| 1 | **ใช้ spare น้อยสุด** (`sp`) |
| 2 | `cost` น้อยสุด (ใกล้→ไกล) |
| 3 | สับน้อยครั้งสุด |
| 4 | I_no ต่ำสุด (เป็น tiebreak สุดท้ายเท่านั้น) |

ส่วนกรณี **ยังไม่บาลานซ์** (ผ่านรีเลย์แต่ spread เกิน) และ **ยังไม่ผ่านรีเลย์** → คงเดิม (ไล่ spread/I_no ต่อ เพราะยังต้องปรับให้ดีขึ้น ตรงนี้ใช้ spare สมเหตุผล)

### ส่วน B — Epsilon band กัน "ดิ้น" เพราะ I_no ต่างกันนิดเดียว
ในทุกจุดที่เทียบ I_no เพื่อ "เลือกให้ดีขึ้น" ให้ถือว่า **I_no ที่ต่างกันไม่เกิน ε (เสนอ ~2 mA) = เท่ากัน** แล้วตกไปตัดสินด้วย spare/cost แทน

ป้องกันเคสที่ spare ตัวหนึ่งกด I_no ได้แค่ 0.3 mA แต่ทำให้ระบบเลือกเปลือง spare เพิ่ม

> ค่า ε ควรเป็นค่าคงที่ตั้งชื่อไว้ เช่น `INO_TIE_MA = 2.0` ที่หัวไฟล์ calculator.js (ปรับได้ที่เดียว) และควรสัมพันธ์กับความละเอียดจริงของหน้างาน

## 4. ทางเลือกเสริม (พิจารณาร่วม)

- **C — จำกัดโควตา spare:** ยอมใช้ spare ได้ไม่เกินจำนวน "ตัวเสีย/outlier จริง" (บวก buffer เล็กน้อย) ไม่แตะ spare เพื่อ marginal gain — เป็น hard-limit ที่เข้าใจง่าย แต่แข็งไป อาจพลาดเคสที่ spare ช่วยบาลานซ์ได้จริง → **แนะนำใช้เป็นเกณฑ์รอง ไม่ใช่ตัวหลัก**
- **D — การ์ดแนะนำ ui.js:** ปรับให้เลือกแผน spare-น้อยในกลุ่มที่ผ่าน → **จำเป็นแต่ไม่พอ** ต้องทำคู่กับ A/B

> **ข้อเสนอหลัก: ทำ A + B** (ครอบคลุม root cause ตรงที่สุด) และคง **budget MAX (12)** ไว้เป็นตัวเลือก "ใช้ทรัพยากรเต็มที่ / I_no ต่ำสุด" สำหรับคนที่ต้องการจริง ๆ

## 6. ผลลัพธ์ที่คาดหวังหลังแก้

- เคสที่ **สลับในแร็คอย่างเดียวก็ผ่าน** → จะ **ไม่ใช้ spare** อีกต่อไป
- เคสที่มีตัวเพี้ยน 1 ตัว → ใช้ spare **เท่าที่จำเป็น** (ไม่ลากไปใช้ทั้งคลัง)
- เพิ่มจำนวน spare ในคลัง → **จำนวน spare ที่ใช้ไม่เพิ่มตาม** (ถ้าแผนเดิมผ่านอยู่แล้ว)
- การ์ด MAX (12) ยังเป็นทางเลือก "ใช้เต็มที่ / I_no ต่ำสุด" ตามเดิม

**Trade-off ที่ต้องยอมรับ:** แผนแนะนำอาจมี I_no สูงกว่าเดิมเล็กน้อย (แต่ยัง < เกณฑ์ และยังบาลานซ์) — นี่คือเจตนา "ผ่านแล้วพอ ประหยัดของ/เวลา"

## 7. แผนทดสอบ (เพิ่มใน `test/swap.test.js`)

1. **บาลานซ์ได้ด้วยแร็คล้วน → spare = 0:** ออกแบบ bank ที่สลับในแร็คแล้วผ่านทั้ง 2 gate ต้องได้ `sparesUsed == 0`
2. **ตัวเพี้ยน 1 ตัว + spare 5 ตัว → ใช้ spare แค่เท่าที่จำเป็น** (ไม่เท่ากับ 5)
3. **เพิ่ม spare แล้วไม่ใช้เพิ่ม:** bank เดิม รัน 2 ครั้งด้วย spare 3 vs 8 ตัว → `sparesUsed` ของการ์ดแนะนำต้องไม่เพิ่ม
4. **ε band:** แผนที่ I_no ต่างกัน < 2 mA ต้องเลือกตัวที่ใช้ spare น้อยกว่า
5. **เคส regression เดิมทั้งหมดต้องยังผ่าน** + ค่า I_no อ้างอิง Excel เท่าเดิม (`test/calc.test.js`)
